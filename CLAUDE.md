## Session Close Rule (MANDATORY)
**Every Claude session that makes changes MUST update the project markdown before ending.**
This is non-negotiable — the markdown is the project's institutional memory.

At the end of every session, update these files (as applicable):
- **`CLAUDE.md`** — add any new gotchas, architectural components, data contracts, or rules discovered. Add to `Known Gotchas`, `Runtime Observability`, or create a new section.
- **`.claude/PARALLEL_RUN.md`** — append to the `## Log` table: date, event name, what was done + commit SHA. Update `## Known issues (active)` if a new data contract or workaround was added.
- **`.claude/PENDING.md`** — update if work was completed or new tasks identified.
- **`METHODOLOGY.md`** — update if any threshold, formula, series ID, or confirmation rule changed.

The update commit message should be: `Docs: update [files] with [session topic]`

If there is nothing to document (no code changes, no discoveries), explicitly confirm that in the session close.

## Quality Bar (CEO-Grade)

This dashboard is published to a CEO-level audience. The bar across
**process governance, data accuracy, visual presentation, and editorial
commentary** is "would not embarrass us in a board deck."

- **Visual contract**: `data/style_guide.md` codifies layout
  conventions, typography, color palette, spacing, chart standards,
  and cross-tab consistency rules. Agent 7 (visual_qa.py) and Agent 8
  (visual_review.py) enforce against this document. New visual checks
  cite the §-section they implement.
- **Data contract**: `data/playbook.md` + `data/known_normal.json` are
  the source of truth for what counts as normal in the data layer.
  Validator passes 1-3h are the enforcement.
- **Editorial contract**: commentary is auto-generated by Agent 3
  (briefing_agent.py), constrained by `data/playbook.md` §2 (commentary
  copy rules — 2-4 sentences, no hedging filler, every numeric must
  match the corresponding KPI tile).
- **Process contract**: every change reaches `main` via PR with smoke
  tests green. Agentic actions go through `_agent_guardrails.py`
  (kill switch, cost cap, path allowlist, audit log). The renderer +
  index.html structure are never modifiable by agents.

When work touches any visible surface, re-run `python scripts/visual_qa.py`
and verify the `Commentary positioned above first chart` plus all
cross-tab consistency checks pass.

## Project Architecture
11-agent Python data pipeline:
0. `scripts/preflight.py` — Agent 0: Pre-flight validates external dependencies before pipeline runs: every FRED series_id used by collector returns ≥1 obs, and every Claude model ID in `scripts/_models.py` is served by Anthropic's `/v1/models`. Halts pipeline immediately on any 4xx. (Self-verification — `docs/SELF_VERIFICATION.md`.) Model IDs are centralised in `scripts/_models.py` (single source of truth) and imported by every agent that calls Anthropic.
1. `scripts/collector.py` — Agent 1: Pulls data from FRED, BLS, EIA APIs
2. `scripts/analyzer.py` — Agent 2: Diffs raw data, scores signals
3. `scripts/briefing_agent.py` — Agent 3: AI commentary (Claude Sonnet)
4. `scripts/renderer.py` — Agent 4: Patches index.html with chart data (regex-based)
5. `scripts/validator.py` — Agent 6: Independent data quality checks (8-pass)
6. `scripts/publisher.py` — Agent 5: Email delivery via Resend
7. `scripts/visual_qa.py` — Agent 7: DOM-based visual quality checks (Playwright)
8. `scripts/visual_review.py` — Agent 8: Vision-based chart review (Claude multimodal)
9. `scripts/earnings_agent.py` — Agent 9: Autonomous quarterly earnings — fetches transcripts, extracts verbatim fields via Claude Sonnet, gated by validator Pass 3c. Runs on its own cron (`earnings_agent.yml`, 10pm UTC during Jan/Apr/Jul/Oct weeks). **Never touches the weekly briefing cadence.**
10. `scripts/repair_agent.py` — Agent 10: Repair agent. Default mode is **observer** — reads `data/validation_report.json` after every CI run and surfaces critical/warning/stale findings into a structured summary in the run log + rolling `data/repair_log.md`. When `AGENT_DIAGNOSTICIAN_ENABLED=1` and `ANTHROPIC_API_KEY` is set, additionally invokes **Stage 10a Diagnostician** (now **memory-aware**): Claude reasons about each finding using `data/playbook.md` + `data/known_normal.json` + the recurrence history from `data/repair_log.md` and `data/incident_reports/`. Recurring findings get upgraded recommendations ("investigate root cause") while first-time findings get downgraded ("monitor"). Writes a per-run incident report to `data/incident_reports/<date>.md`. Still read-only — no code/data/layout writes ever. Every LLM call is bounded by `scripts/_agent_guardrails.py` (kill switch via `AGENT_DISABLE_ALL=1`, cost cap via `AGENT_MAX_LLM_CALLS`, path allowlist) and logged to `data/agent_memory.jsonl`. Future stages (10b Proposer with diff, 10c Auto-fixer) require ≥3 weeks of 10a shadow data before promotion. Runs `if: always()` after Agent 6 so it surfaces failures even when the validator gate halts the pipeline.

Supporting modules (read by agentic components):
- `scripts/_models.py` — Centralised Claude model IDs (single source of truth).
- `scripts/_agent_guardrails.py` — Runtime safety layer for LLM-driven agents. Hard kill switch, cost cap, path allowlist, two-LLM critique helper. **Every agentic LLM call goes through `bounded_llm_call()` so it's audited.**
- `scripts/_agent_memory.py` — Append-only JSONL audit log writer at `data/agent_memory.jsonl`. Capped at 2000 entries (rolling FIFO).
- `scripts/_signal_rationales.py` — **Phase 2 explainer** (post-analyzer narrative augmentation). When `AGENT_EXPLAINER_ENABLED=1` + `ANTHROPIC_API_KEY` are set, reads `data/signals.json` + `data/raw_data.json` and emits a Claude-authored rationale per flagged signal to `data/signal_rationales.json` (separate artifact — does NOT mutate signals.json, renderer is unchanged). Same guardrails as Agent 10. Read-only narrative; never recommends actions.
- `scripts/inspect_agent_memory.py` — CLI for reviewing the audit log (`python scripts/inspect_agent_memory.py --tail 20 --full` etc.). Read-only.
- `scripts/_editorial_review.py` — **Phase 2.5 editorial auditor**. Reviews every per-tab commentary in `index.html` + briefing-agent commentary fields in `signals.json` against `data/style_guide.md` §2 (length, vocabulary, factual grounding). Deterministic linters run first (length, forbidden vocab, hedging filler, fabricated-numeric detection); LLM tone/factuality pass is opt-in via `AGENT_EDITORIAL_REVIEW_ENABLED=1` and uses two-LLM critique (Sonnet audits, Opus critiques) before any "critical" verdict is promoted. Output: `data/editorial_report.json`. Read-only — never modifies commentary.
- `scripts/ceo_grade_gate.py` — **CEO-grade pre-deploy gate**. Deterministic orchestrator that reads the verdict artifacts from validator, visual_qa, vision_review, editorial_review, and today's repair incident report and produces one go/no-go decision in `data/ceo_grade_verdict.json`. No LLM calls of its own — replay-safe and idempotent. Use `--strict` to treat warnings as gate-blocking on publication days. Exit codes: 0=PASS/WARN, 2=FAIL, 3=SKIP (missing layer), 4=internal error.
- `data/playbook.md` — Human-curated reasoning context. Pipeline cadence, source publish lag tables, noise floors per series, common-cause patterns, forbidden recommendations. Agents cite §X.Y when justifying diagnoses; when this and an LLM disagree, this file wins.
- `data/known_normal.json` — Machine-readable mirror of playbook baselines (publish lag, noise floors, shock-tracker min obs counts, model routing).

Supporting scripts:
- `scripts/snapshot.py` — Rolling data backups (keep last 13, ≈ one quarter of weekly runs). Each snapshot includes `raw_data.json`, `validation_report.json`, and `index.html` so a rollback can restore the live page directly when the renderer itself is the regression. Override retention via `SNAPSHOT_MAX` env var; rollback with `--rollback YYYY-MM-DD [--include-html]`.
- `scripts/healthcheck.py` — Post-deploy page verification
- `scripts/version_tracker.py` — Pipeline run audit trail

## Known Gotchas
- BLS values are strings (e.g., `'23756.5'`), always use `round(float(val))` not `int(val)`
- `json.dumps` produces `\u` escapes — always use `lambda m: replacement` in `re.subn`, never raw strings
- FRED single-value endpoints return `{"date": "...", "value": 4.25}` dicts, not scalars
- Running renderer twice on same HTML causes benign `patch_kpi` warnings (labels already updated)
- PCE staleness warnings are genuine data lag (~95 day publication delay), not bugs
- Regex-replace patterns in `renderer.py` must match the JSON shape the renderer *itself writes back* — `json.dumps(..., separators=(', ', ':'))` produces single-line output, so patterns requiring `\n};` will silently fail after the first run (see `update_shock_tracker`)
- UMich Consumer Sentiment: collector pulls direct from `sca.isr.umich.edu/files/tbcics.csv` first (gives prelim ~2 weeks before FRED's embargoed final). `umcsent` entries carry a `status` field (`'preliminary'` or `'final'`) — renderer/KPI/validator all treat missing status as `'final'` for back-compat
- **`_api_writer._STATE_FILE` is hardcoded** — `scripts/_api_writer.py` writes to `_ROOT / 'data' / 'state.json'` by default. Override with `MACRO_STATE_FILE` env var (set by smoke tests for test isolation). Never add a test that calls `renderer.render()` without first save/restoring `_api_writer._STATE_FILE` and `_api_writer._STATE` — otherwise smoke tests overwrite the live `state.json` with fixture data, causing every Tier-1 chart to render null on the next pipeline run.
- **FRED NPPTTL discontinued 2022-05-01** — the `NFP_VS_ADP.adp` array will always have only 1-3 filled values out of 13 (from `adp_latest` + `_ADP_VERIFIED`). The `SPARSE_OK['NFP_VS_ADP.adp'] = 8` override in both `visual_qa.py` and `validator.py` reflects this permanent data contract. Do not raise this threshold — the data is correct.
- **`buildJobsTab()` null guard** — if `NFP_VS_ADP` is missing from `state.json`, the jobs tab returns early and all 4 charts blank silently. The cold-start bootstrap in `renderer.py` (initializing `adp_arr = [None] * len(lbl_12)` when all ADP fallbacks fail) prevents this. If jobs charts are blank, check `data/state.json` for the `NFP_VS_ADP` key first.
- **Panel subtitle gate string contract** — `render_inflation()` and `render_labor()` gate PCE/CPI/SECTOR_MOM/U_SECTOR_MOM panel-sub month updates on `any(s.startswith('XXX registered') for s in applied)`. If a rebuild function changes its success message (e.g. Tier 1 migration changed `'XXX rebuilt'` → `'XXX registered to state.json...'`), the gate silently stays False and the subtitle freezes — Pass 3d fires as critical every run. Smoke test `test_panel_subtitle_gates` guards this contract. Rule: when editing any `rebuild_*` success message, update all downstream `startswith()` gates in `render_inflation` and `render_labor` to match.
- **Commentary auto-patch silent failure** — `render_inflation()` and `render_labor()` maintain "stale commentary" patches that update KPI numbers (Core PCE, U-3, NFP) in the HTML when Agent 3 doesn't refresh them. These use `re.subn` + `_record_subn_result` and only call `applied.append(...)` when `n > 0`. If a format mismatch occurs, a `warnings.append` fires instead — check the renderer summary for `Commentary Core PCE: no matching sentence format` warnings. Core PCE uses a two-tier regex: tier-1 matches Agent 3's structured `<strong>+X.X% YoY</strong>` format; tier-2 matches plain-text `"Core PCE at X.X%"` variants. Smoke test `test_commentary_patch_regexes` guards both tiers. The KPI tile (live data) and commentary text (LLM prose) can still diverge if Agent 3 fails AND neither tier matches — this surfaces as a warning, not a silent pass.
- **Dark mode `body.themed-sm` orphan** — `theme-overlay.css` styles under `body.themed-sm` have no automatic dark-mode equivalents. Any time a visual regression appears only in dark mode (not light), check whether the fix lives in `theme-overlay.css` under `body.themed-sm` — dark mode needs a `:root[data-theme="dark"]` mirror. Known cases: (1) `.dtable td` loses `padding:12px; vertical-align:top` → §24.35 adds the dark mirror; (2) narrative column min-widths (`#fc-scenarios-tbl [data-label="Key View"]` etc.) cause row heights of ~200px → §24.35 adds min-width constraints. When adding new `body.themed-sm` rules to `theme-overlay.css` (read-only), always add the `:root[data-theme="dark"]` counterpart in `index.html` in the same session.
- **`body.themed-sm` is the actual default skin, not just a dark-mode counterpart** — a fresh page load has `body` classes `sidebar-active themed-sm` with no `data-theme` attribute at all; `theme-overlay.css`'s `body.themed-sm` rules use `!important` and ARE the default (light) styling layer, distinct from and higher-priority than any unscoped rule written directly in `index.html`. This bites outside dark mode too: adding a new unscoped CSS rule (e.g. `.kpi.hero .kpi-val{font-size:28px}`) can be silently absorbed by a pre-existing `body.themed-sm .kpi-val{font-size:30px!important}` in the read-only `theme-overlay.css`, with zero visible effect and no console error. Symptom: `getComputedStyle()` on the live page shows a value that matches neither your new rule nor the value you expected — check `document.body.className` for `themed-sm` first. Fix pattern: add a matching `body.themed-sm <your-selector>{...!important}` override directly in `index.html`'s `<style>` block (never edit `theme-overlay.css`) with enough added specificity to win over the existing `!important` rule. Example: `.kpi.hero .kpi-val` needed `body.themed-sm .kpi.hero .kpi-val{font-size:36px!important}` because `body.themed-sm .kpi-val{font-size:30px!important}` already existed and unconditionally beat the unscoped 28px hero rule.
- **`python tests/test_smoke.py` used to leave the working tree dirty — fixed 2026-06-30, commit `964318e`.** Root cause was two-fold, not the snapshot/rollback path originally suspected: (1) `test_renderer_idempotent()`'s second `renderer.render()` call never re-applied the `_api_writer._STATE_FILE` tmp_dir redirect that `test_renderer()` restores to the real path in its `finally` block, so it silently overwrote live `data/state.json` every run; (2) `validator.validate()` (invoked by `test_validator_offline`) runs a real Playwright visual-QA pass via `check_visual()`/`check_visual_review()`, and `visual_qa.py`/`visual_review.py` resolve file paths from repo `ROOT` rather than a redirectable module global, corrupting `data/screenshots/*.png` + `data/visual_qa_report.json`. Fix: a `MACRO_SKIP_VISUAL_QA` env gate (mirrors the existing `FRED_API_KEY`/`BLS_API_KEY` offline-mode pattern) that the smoke test now sets, plus a fix to `test_snapshot()`'s incomplete `STATE_FILE`/`SIGNALS_FILE` redirect. `test_no_real_file_mutation()` is a new regression guard — fingerprints the at-risk real files before the suite runs and fails loudly if any changed, independent of git. If `git status` ever shows `data/state.json` or `data/screenshots/*` dirty after a smoke run again, this guard should catch it immediately — treat that as a real regression, not environmental noise.
- **Adding a new tab touches ~9 locations, not just one `.tab-panel` div.** When the Pulse tab was split out from Outlook (2026-07-01), the nav/build wiring required updating: (1) both `_GRP` and `_GRPS` nav arrays (top nav + sidebar duplicate the same `{t:'id',l:'Label'}` tab list independently — always edit both); (2) both `_IC` icon-map objects (same top-nav/sidebar duplication pattern); (3) the two hardcoded default-tab activation calls, `_b52_activateTab('fc')` and `_nsb_sync('fc')`, if the new tab should be the default landing tab; (4) `TAB_NAMES` and `TAB_IDS` in `index.html` (used by the PDF/HTML download-export feature — a missing entry there means the exported file silently omits the tab); (5) `TAB_IDS`/`TAB_NAMES` in `scripts/visual_qa.py` **separately** — this list drives which tabs the 446+ DOM checks actually visit, so a new tab with zero entries here gets zero regression coverage and visual_qa.py will report a clean pass while never having looked at it. A `.tab-panel` div existing in the HTML is necessary but nowhere near sufficient for a tab to be fully wired — grep for the old tab id across the whole file before considering a new-tab addition done.
- **`theme-overlay.css` (light/themed-sm) frequently has newer, deliberately-reasoned design decisions than dark mode or `style_guide.md` — check dates/comments before "fixing" a cross-theme divergence in either direction.** Three separate instances found 2026-07-01: `.kpi-val` font-family (theme-overlay.css's `DM Serif Display` — with its own `check_serif_scope` enforcement and a dated "print-grade numeric typography" pass — vs. dark mode's stale `Instrument Serif` fallback), and `.panel-title` size (theme-overlay.css's `17px` — with a comment explaining it fixed a prior 22px-serif hierarchy-competition problem — vs. dark mode's stale `13px`). In both cases `style_guide.md` documented the OLD dark-mode value, not the newer themed-sm one — the docs hadn't been updated when the light-mode fix landed. Resolution both times: treat the themed-sm value as canonical (it has more context/reasoning behind it), backport to dark mode, update `style_guide.md` to match. Do not assume dark mode or the style guide is the source of truth by default — check which side has the explanatory comment and the more recent rationale.
- **The `.kpi-val`/`.panel-title` base rules index.html actually falls through to live in an unscoped "MACROLENS COMMERCIAL THEME v2" block (~line 2384+), not where you'd expect.** Dark mode has no explicit font-family/size override for these, so it inherits whatever this unscoped, `!important`, later-cascade block says — which is easy to miss when searching for `:root[data-theme="dark"]`-prefixed rules specifically. When a dark-mode value doesn't match any dark-scoped selector you can find, check this block before assuming it's hardcoded somewhere theme-specific.
- **`:root[data-theme="dark"] X` is strictly MORE specific than a bare `X`, not equally specific — do not reason about this cascade by "source order" alone, and do not trust an LLM's textual cascade analysis without empirically verifying with `getComputedStyle`.** A 2026-07-01 audit workflow asked two agents to read `theme-overlay.css` + `index.html`'s CSS as text and reason about which rules win; it produced ~17 claimed divergences based on the (wrong) assumption that a dark-scoped `!important` rule and a later unscoped `!important` rule "tie" on specificity and the later one wins — e.g. it claimed the §24.12 `.panel-title` and §24.35 `.dtable td` fixes were being silently cancelled by the later unscoped "MACROLENS COMMERCIAL THEME v2" block. Direct `getComputedStyle` checks in a live browser showed both fixes fully intact — the attribute selector in `:root[data-theme="dark"]` adds real specificity (10 points, same tier as a class), so a dark-scoped rule beats an equal-`!important` unscoped rule regardless of which comes later in the file. Of ~17 claimed divergences, only 6 were real when empirically checked. **Rule: any CSS divergence claim from reading source text (by you or an agent) must be confirmed with a live `getComputedStyle` measurement in both themes before you act on it — never fix a "bug" based on cascade theory alone.**
- **`body.themed-sm .kpi-val{color:#0D1B2A!important}` (theme-overlay.css) silently killed the entire semantic red/green/amber KPI color system in light mode.** `_kpiColor(metric,val)` computes the correct per-tile hex and the render function writes it as an inline `style="color:${col}"` — but a class-selector `!important` in an external stylesheet always beats a plain (non-`!important`) inline style regardless of specificity, so every KPI value rendered the same near-black in light mode no matter what color was computed (confirmed via `getComputedStyle` showing `rgb(13,27,42)` on every tile despite each having a different inline `color:#XXXXXX`). Dark mode had no competing rule and rendered correctly, which is what made this visible: a user screenshot comparison showed colored values in dark, monochrome in light. **Fix pattern: add `!important` to the inline style itself** (`style="color:${col}!important"`) — inline `!important` outranks a class-selector `!important`, restoring the color without touching the read-only `theme-overlay.css`. Same class of bug as the font/padding cascade issues above (a themed-sm rule silently overpowering something it shouldn't) — whenever a value looks "washed out" or uniformly neutral in one theme but not the other, suspect a forced-color `!important` rule beating a non-`!important` inline style, and check with `getComputedStyle` + `getAttribute('style')` side by side (the inline attribute shows JS intent; computed style shows what actually wins). **Superseded 2026-07-01**: `_kpiColor()` no longer computes red/green/amber threshold status for the main value — see the entry below. The `!important` inline-style mechanism this entry describes is still how the color (now purple-or-neutral) gets applied; only what color means changed.
- **Design principle (2026-07-01, from a 2-expert review): don't encode two different semantic dimensions with the same color vocabulary on adjacent elements.** The KPI strip used to color the main value by *absolute threshold status* (green/amber/red zone) while the adjacent delta badge was colored *independently* by *direction of change* — two unrelated dimensions sharing one red/green/amber palette, which could visually disagree (e.g. a metric sitting in the red zone that had just improved showed a red value next to a green up-arrow on the same tile). Fixed by reserving color for direction-of-change only (the delta badge, which already has a redundant arrow glyph) and making the absolute-status main value neutral, with a rare non-color cue (red left-border + dot) reserved for genuine red-zone alerts only — not amber/green, so it stays meaningful rather than becoming permanent wallpaper. `_kpiColor()` / `_kpiIsAlert()` in `index.html` implement this. **Apply this same principle if any other tab's threshold-colored values get touched** (sector cards, bank earnings trend pills, forecast tables) — check whether they have their own independent delta/direction coloring nearby before assuming the absolute-status color is the only signal in play.
- **Some JS-generated components compute an `_isDark` flag and use it correctly for SOME colors but not others — check every hardcoded hex in a function, not just the ones already branched.** Found 2026-07-01 in the Oil tab's shock tracker (`SHOCK_TRACKER.phases` render function, ~line 7092): it already computed `_isDark` and branched `statusCfg` (the Confirmed/Not Yet/etc. badges) correctly per-theme, but the metric label/value text (`#94A3B8`/`#64748B`) and the three header cards' backgrounds (`#FFFBEB`/`#F8FAFC`/`#F0FDF4`) were hardcoded with zero branching — each color happened to pass contrast in only the ONE theme it was originally tuned against (label passed dark 6.26:1 but failed light 2.56:1; value passed light 4.76:1 but failed dark 3.37:1). This is the same "themed-sm has an orphan" bug class as the CSS-cascade gotchas above, just inside inline JS-generated HTML instead of a stylesheet. **When auditing a component for theme-awareness, grep the whole function for every hex literal — don't stop once you find one correctly-branched piece (like a status-badge palette) and assume the rest follows the same pattern.**
- **Fixing a hardcoded color's TEXT for dark mode without also checking its BACKGROUND can make contrast worse, not better.** Near-miss caught while doing the shock-tracker fix above: an initial pass changed a header card's value text to near-white for dark mode, but the card's background was still hardcoded light (`#F8FAFC`) with no dark branch — that would have shipped near-white-on-white, a worse failure than the original dark-navy-on-light it replaced. Always check both text AND its actual container background together (walk up from the text node to the nearest non-transparent `background-color`) before considering a per-theme color fix complete.
- **This same component's colors are baked into inline styles at tab-build time, not live CSS variables — a `toggleTheme()` JS call after the tab has already rendered will NOT retroactively repaint it.** Unlike `var(--text)`-based CSS (which updates live when the `data-theme` attribute/class changes), `SHOCK_TRACKER`'s render function computes literal hex values once when `buildOilTab()` first runs and writes them into `innerHTML` — toggling theme afterward changes the `data-theme` attribute but does nothing to already-rendered inline styles. When testing any JS-generated (not CSS-only) component across themes, always do a genuine `location.reload(true)` starting in each theme — a `toggleTheme()` call mid-session will show you stale colors and produce a false read, same root cause as the earlier "toggleTheme() vs real reload" cache gotcha but for a different reason (JS staleness, not browser cache). **The real theme persistence key is `md_theme` in `localStorage`** (`MD.toggleTheme` reads/writes it directly, ~line 350/367) — don't guess a plausible-sounding key name when scripting a theme-forced reload, verify it in source first.
- **This "hardcoded pastel background in dark mode" bug is confirmed systemic — 3 instances found in one session** (Oil tab shock tracker; Fed Rates tab treasury-yield explainer panels; Oil tab's WTI/Brent/Crisis Range daily-summary tiles), found via 2 user screenshots plus one direct user question, **zero of the three caught by `visual_qa.py`'s 449 checks**. Two sub-shapes seen so far: (a) text correctly uses `var(--text2)` but the wrapping background is a hardcoded light pastel with no `_isDark` branch — dark mode's light `--text2` value lands on a background that never left light mode; (b) *both* background AND text hardcoded with zero theme awareness at all (the daily-tiles case — worse, since even light mode had a pre-existing marginal contrast bug on the label text that nobody had separately caught either). A reusable fix palette has emerged across all 3 fixes — reuse it rather than inventing new values each time: `_mutedTxt = _isDark ? '#94A3B8' : '#64748B'`, `_valTxt = _isDark ? '#A8C4D8' : '#334E68'`, backgrounds go from a light hex to `rgba(<accent-rgb>,.06-.10)` translucent tints in dark. A follow-up sweep task is spawned and pending (`task_3b7bae9e`) — with 3 confirmed instances this is now worth prioritizing over waiting for a 4th to surface by accident. **Also recurring across all 3 fixes: an ad-hoc contrast-verification script using a naive `/[\d.]+/g` regex mis-parses hex literals** (extracts only the digit characters, silently dropping A-F, e.g. `#94A3B8` → wrongly parsed as rgb(94,3,8)) — always use a proper `parseInt(hex.substr(n,2),16)` hex parser for verification math, and if a contrast number looks implausibly high or low, suspect this before trusting it.
- **When mirroring a `body.themed-sm` layout rule (padding/margin/width) into dark mode, always check for a nested higher-specificity override inside the SAME rule block before assuming a lower-specificity rule elsewhere already handles it.** The 2026-07-01 body-padding parity fix (commit `3615a28`) added `:root[data-theme="dark"] body{padding:32px 48px 80px!important}` but skipped mirroring `theme-overlay.css`'s `@media(min-width:901px){body.themed-sm.sidebar-active{padding-left:240px!important}}` override, on the wrong assumption that the 240px sidebar offset was "theme-agnostic and already handled elsewhere." It wasn't — the new dark-scoped rule's specificity (`:root[data-theme="dark"] body` ≈ attribute+element) beat whatever lower-specificity theme-agnostic sidebar rule existed, silently resetting padding-left to 48px and sliding all page content under the fixed 220px sidebar from 901px up to 1920px viewport width (below 900px the sidebar hides; above 1920px a separate override already existed). Caught via user screenshot ("sidebar and canvas overlapping"), fixed in commit `2732fd0` by adding the missing `@media(min-width:901px)` mirror. **Lesson: `getComputedStyle` checks at ONE viewport width (e.g. 1440px, matching whatever the toggle-vs-reload state happened to be) are not sufficient for a padding/layout fix — test a clean (cache-bypassed, `location.reload(true)`) page load at multiple representative widths spanning every breakpoint the light-mode source defines, not just the width the bug report screenshot happened to show.** A `toggleTheme()` JS call and a real page reload can show different results if a browser cache serves stale CSS — always hard-reload when verifying a CSS fix, not just call the theme-toggle function.
- **A dark-mode "sharpness compensation" rule (§24.33) can undershoot if the light-mode baseline it was written against later changes.** §24.33 bumps dark-mode font-weight up (e.g. 400→500) to compensate for halation (bright text on dark canvas reads thinner than the same weight on light). Found 2026-07-01: two of its target selectors (`.m-lbl`, `.panel-sub`) have an actual light-mode weight of 700, not the 400/500 the rule assumed — so the "boost" to 500 rendered dark-mode LIGHTER than light, the opposite of the intended effect. When touching any halation/sharpness-compensation rule, verify the CURRENT light-mode weight first (`getComputedStyle`, not the rule's own comment) — the assumption it was written against may be stale.

## Runtime Observability (dev — `index.html`)
Four layers added 2026-05-30 to catch blank charts before users see them:

1. **`window.MD._errors[]`** — global JS error accumulator. Initialized before `<title>` via `onerror` + `onunhandledrejection` hooks. Every tab crash, hydration failure, and unhandled rejection is appended here with `{type, msg, stack, ts}`.
2. **`window.MD._hydrationSuccess`** / **`window.MD._hydrationMissingKeys`** — set in `_hydrate()` bootloader. If state.json is unreachable, `_hydrationSuccess = false` and an entry is pushed to `_errors[]`. `_hydrationMissingKeys` lists any Tier-1 keys absent from the fetched payload.
3. **`_safeBuild(tabName, buildFn)`** — wraps all 15 tab dispatch calls. Catches any `buildXxxTab()` exception, records it in `window.MD._errors[]` with tab name + stack trace, and logs to console. Prevents a single bad tab from killing others.
4. **visual_qa runtime sweep** (§QA-observability) — after all tab checks, reads `window.MD._errors` via `page.evaluate()`. Hydration failure → critical. Tab crash → critical. Other errors → warning. Chart.js instance check (§QA-chartjs) verifies every visible canvas has a live `Chart.getChart()` instance, not just DOM presence.

Also: `.github/workflows/observability.yml` — runs every 6 hours, checks prod + dev URLs via `scripts/healthcheck.py`, opens a GitHub issue on failure, adds comments on repeat failures, auto-closes on recovery. Secrets: `PROD_URL` (defaults to GitHub Pages URL), `DEV_URL` (optional; check skipped if absent).

## Earnings Commentary — Factuality Rule (project skill)
Applies to `BANK_COMMENTARY`, `BANK_THEMES`, `BANK_RESULTS`, earnings-call panels in `index.html`, and any narrative block sourced from a company disclosure.

- **Only real, attributable content.** Every CEO/CFO quote must be a verbatim excerpt from an actual earnings call transcript, press release, or 10-Q/10-K filed by that company. No paraphrases in quotation marks. No composed sentences written in an executive's voice.
- **No implication, no fabrication.** Do not write forward-looking guidance, NCO rates, EPS, NIM, or headcount numbers unless the figure is published by the company. If a company hasn't reported yet (e.g. Barclays BCUS on Apr 30 before it happens), mark it `Pending` — do not pre-fill with estimates.
- **Cite the source channel** via the `src` field tag (`Prepared` / `Q&A` / `Summary` / `Pending` / `FY25 Call`). If you can't point to a transcript line or filing page, the content doesn't ship.
- **Verify before editing.** Before modifying a quote or figure in an earnings card, read the underlying source (transcript URL, press-release PDF, or 10-Q) and paste the matching snippet in the commit message. "Touched up wording" is not allowed — either the quote is verbatim or it becomes a non-quoted summary.
- **When in doubt, remove — don't smooth.** If a sentence reads well but you can't source it, delete it rather than rephrasing it into plausibility.
- **Structural redesigns need sources first.** Expanding the card schema (e.g. adding Performance Trends / Credit Performance / Regulation / Tech-AI sub-sections) requires sourced content for every new field per bank before any template change lands. Do not ship a new template populated with AI-generated filler.
- **Auditing checklist** before any commit that touches this data:
  1. Every `quote` field traces to a transcript line.
  2. Every numeric (NCO, NII, EPS, NIM, volumes) matches the company's released figure.
  3. Future-dated items (reports after today's date) are marked `Pending`.
  4. Source attribution in the panel footer lists each call date used.

### Update Workflow (Q2 2026 onward)
The earnings commentary is **data-driven** — do not hand-edit `index.html`. Flow:

1. **Edit `data/bank_earnings.json`** — add/update each bank's `actual_report_date`, `transcript_url`, `quote`, and the 7 field entries (`economy`, `lending`, `cards_loans`, `macro`, `tech_ai`, `credit`, `outlook`). Set `status` to `reported` once actual data is in. Leave `pending` for banks whose call hasn't happened yet.
2. **Archive the transcript** to `data/transcripts/<Quarter>/<TICKER>.txt` (e.g. `data/transcripts/Q2_2026/JPM.txt`) — plain text of the call is fine. This enables the validator's verbatim gate for this bank.
3. **Run `python scripts/renderer.py`** — patches `BANK_COMMENTARY` in `index.html` from the JSON. Date with `(pending)` suffix is rendered automatically for banks whose `actual_report_date` is missing or in the future.
4. **Run `python scripts/validator.py`** — Pass 3c (`check_earnings_verbatim`) verifies every quoted span in your JSON exists verbatim in the archived transcript. A mismatch is build-blocking (critical severity).
5. **Update the panel footer `src=...` line** in `index.html` by hand for now (sources attribution — not yet automated).

When the reporting date list changes quarter-to-quarter, update `expected_report_date` per bank in the JSON (single field, one place).
